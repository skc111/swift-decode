# Swift Decode：从一条回答开始，学懂单卡推理加速

这是一份可以从头顺着读的教程。你只需要会一点 Python，并知道 GPU 可以执行大量数值计算。遇到新术语时，我们先用例子说明它在做什么，再给出英文名和代码位置。

Swift Decode 要解决的事情是：**在一张 RTX 5090 32GB 显卡上运行一个 27B 模型，让一个请求的回答生成得更快，并检查加速前后的输出是否一致。** 27B 表示模型参数规模约为 270 亿。

本文一直使用同一个小例子：用户给出输入 `P`，模型原本会依次回答 `A、B、C、X`。比如你可以把它想象成补全“天空是”，然后依次看到“蓝、色、的、。”。为便于演示，我们暂把这四小段各视为一个 token，并用字母代替；真实 tokenizer 怎样切分，需以实际结果为准。

先跟清楚这四段回答怎样生成，再看真实代码和实验数据。

不需要开 GPU，也不需要下载任何东西。正文中的教学数值会明确标注；第 9 课中的性能表来自已经完成的云端实验。

## 第 1 课：模型怎样选出一个 token

先只研究一件事：用户输入一句话，模型怎样决定回答的第一小段内容。

### 1.1 文本先变成编号

GPU 上的模型做数值计算，因此程序先把文本切成一些片段，再把片段变成整数编号。完成这件事的工具叫 **tokenizer，分词器**；每个被编号的片段叫 **token**。

一个汉字、一个英文词，不一定恰好对应一个 token。真实切分由 tokenizer 决定。下面只画过程，不给示意句子编造真实 token ID：

```text
用户输入：“请补全：天空是”
                  ↓ tokenizer
              一串整数编号
                  ↓ 模型
              下一个 token 的编号
                  ↓ tokenizer 解码
              可以显示的文本片段
```

之后我们把整段输入简写为 `P`。`P` 可能包含很多 token；`A、B、C、X` 则各代表一个输出 token。

### 1.2 模型给每个候选打分

先只列出 A、B、C、X 四个候选。真实词表还包含许多其他候选，此处省略。

模型读完 P 后，可能给出下面这组**教学分数**：

| 候选 | 分数 |
|---|---:|
| A | 8.5 |
| B | 6.2 |
| C | 2.1 |
| X | 1.0 |

我们使用的选择规则是：**选分数最高的那个**。因此，第一个输出是 A。

这些还没有转成概率的分数叫 **logits**。从一组数中找到最大值对应的位置，叫 **argmax**。每次都这样选词的生成方式叫 **greedy decoding，贪心解码**。

先记住这条关系就够了：

```text
模型给所有候选打分 → argmax 选最高分 → 输出一个 token
```

### 1.3 hidden 是打分之前的一串数

模型不会从 token 编号直接跳到最后的分数。中间会经过多层计算，每一层都把当前位置表示成一串浮点数。

比如，教学上可以把这串数画成：

```text
[0.2, -1.0, 0.7, ...]
```

它叫 **hidden state，隐藏表示**。这里的 hidden 表示模型内部的数值表示。它不是最终输出的文字。

最后，一个输出层把 hidden 变成整个词表的分数。这个输出层在代码中叫 `lm_head`。

```text
token 编号
    ↓ 查 embedding：把编号变成向量
多层模型计算
    ↓
最终 hidden：一串表示当前位置的数
    ↓ lm_head：输出层
logits：每个候选 token 的分数
    ↓ argmax
选中的 token 编号
```

**embedding** 就是“编号到向量”的查表过程。**向量**在这里可以先理解为一维数组。**张量**则是这些数值数组的通称，可以是一维、二维或者更多维。

到这里，你已经认识了排障时最重要的三个对象：token 是选了谁，logits 是为什么选它，hidden 是打分之前模型算出了什么。

### 1.4 模型参数和运行状态有什么区别

模型参数也叫权重。它们是训练得到、推理时反复使用的数值。

你可以这样区分：

| 对象 | 在一次回答中会不会持续变化 | 例子 |
|---|---|---|
| 权重 | 通常保持不变 | 把 hidden 转成 logits 的矩阵 |
| 当前输入和中间结果 | 每一步变化 | 当前 token、hidden、logits |
| 历史状态 | 随着处理的 token 更新 | 已经算过的历史信息 |

**推理引擎**负责把权重放进显存，安排这些计算，并管理每一步的历史状态。Swift Decode 的工作就在这一层。本项目运行推理，不更新模型参数。

### 小练习：从哪里开始查错

两次运行都输入同一个 P，却分别选了 A 和 B。你已经拿到了两组 logits。下一步先看什么？

<details>
<summary>展开答案与原因</summary>

先看两组分数是否不同，以及各自的最大值对应哪个 token。

如果分数相同、程序却输出不同 token，就应检查选词或输出收集逻辑。如果分数本身不同，则继续往前查 hidden 或更早的计算。

这样能把“模型算出了不同结果”和“程序把结果取错了”分开。

</details>

## 第 2 课：把 A、B、C、X 一步步生成出来

第 1 课只拿到了第一个 A。现在继续生成后面的 B、C、X。

### 2.1 为什么通常要一个接一个地生成

我们研究的生成方式中，下一个 token 的选择依赖已有前文。

```text
读完 P           → 预测 A
已有前文 P,A     → 预测 B
已有前文 P,A,B   → 预测 C
已有前文 P,A,B,C → 预测 X
```

这种让输出继续成为后续输入的方式，叫 **自回归生成**。

历史信息可以缓存起来，所以实际运行不必每次把整段 P 从头重算。引擎可以在已经保存的状态上继续处理新 token。

### 2.2 Prefill 是处理已知输入

P 在用户提交请求时已经完整给出。处理这段输入、建立历史状态，并产生第一个 A，叫 **Prefill，预填充**。

“预填充”这个名字说的就是：先把输入对应的历史状态填好，后面继续生成时可以使用。

此时发生了一件容易忽略的事：

> 模型处理了 P，预测出 A。A 已经可以显示给用户，但模型还没有把 A 当作新的输入处理过。

我们用一张表跟踪全过程。假设这次只要求输出四个 token：

| 时刻 | 已经显示的回答 | 模型已经处理过的内容 | 下一步要送入什么 |
|---|---|---|---|
| 请求开始 | 空 | 还没有本请求的历史 | P |
| Prefill 结束 | A | P | A |
| 第一次后续计算结束 | A B | P,A | B |
| 第二次后续计算结束 | A B C | P,A,B | C |
| 第三次后续计算结束 | A B C X | P,A,B,C | 已达四个输出，停止 |

表中最后一行，X 已经是有效输出，但没有必要再处理 X，因为我们已经决定结束回答。

### 2.3 Decode 是继续产生后续 token

Prefill 之后，利用已有历史继续生成的阶段，叫 **Decode，解码**。

这里说的是“模型继续生成”的阶段。Tokenizer 把编号转换成可读文字时也叫解码，那是另外一个转换动作。

本例里：

```text
Prefill 产生：A
Decode 产生：B、C、X
```

所以生成四个 token，Prefill 之后只需要再产生三个 token。这会影响后面速度指标的分子。

代码常把一次推进叫一个 **step，步骤**。普通解码的一步通常只产生一个新 token；学到投机解码以后，你会看到一步也可以产生多个新 token。

### 2.4 两个阶段为什么用时特点不同

Prefill 已经知道 P 中所有 token，因此许多矩阵运算可以一次处理很多位置。普通 Decode 通常只有一个新位置可以处理。

可以把一个线性层暂时看成“拿输入数组去乘一张很大的权重表”：

```text
Prefill：读入一块权重，让它服务许多输入位置。
Decode：读入一块权重，通常只服务一个输入位置。
```

后者每产生一个 token，都可能需要读取大量权重。如果还有很多小操作需要不断提交给 GPU，调度也会花时间。

这是本项目优化方向的来源。具体是读取权重更慢，还是算术运算更慢，需要实际测量；此处先理解为什么两阶段值得分开分析。

### 小练习：已经输出是否等于已经处理

表中刚显示 `A B C` 时，模型处理过 C 吗？下一次输入是什么？

<details>
<summary>展开答案与原因</summary>

还没有处理 C。它刚处理完 B，预测出 C。下一次输入是 C，处理以后才会预测 X。

记住“预测出的 token 会成为下一步输入”，第 7 课的状态槽位就不会差一位。

</details>

## 第 3 课：模型怎样记住前文

现在我们知道，处理 A 时需要用到 P，处理 B 时需要用到 P,A。接下来研究这些历史信息存在哪里。

### 3.1 先理解注意力是在取历史信息

**Attention，注意力**，是一类从历史位置读取信息的计算。

当前 token 会形成一个查询向量，叫 **Query，Q**。每个历史位置保存用于匹配的 **Key，K**，以及被读取的 **Value，V**。

可以按动作理解：

```text
当前 Q 与历史 K 计算匹配程度
                ↓
得到各历史位置的权重
                ↓
按权重汇总历史 V
```

这里的 Q、K、V 都是数值向量。它们是模型算出的表示。

已经处理过 P 后，P 的 K/V 不会因为我们又生成了 A 就必须全部重新计算。因此，引擎可以保存它们。这个存储区域叫 **KV Cache**。

### 3.2 用一张表看缓存怎样增长

下面只画一个注意力层，并省略 P 内部的多个位置：

| 处理进度 | 有效的 KV 内容 |
|---|---|
| 处理完 P | P 的 K/V |
| 再处理 A | P 的 K/V，A 的 K/V |
| 再处理 B | P 的 K/V，A 的 K/V，B 的 K/V |

缓存避免了重复计算历史 K/V，但新查询仍然要访问有效历史。全注意力的历史越长，需要保存和读取的 K/V 通常也越多。

本项目提前分配缓存空间。本轮实验最多为 4096 个位置准备空间；实际请求可能只用了其中一小段。

这和 Python 列表里“已经写入几个元素”是两个概念：**分配了多少空间**与**哪些位置现在有效**，需要分别管理。

<details>
<summary>想对照代码：KV 的形状和容量公式</summary>

K 和 V 分别保存为：

```text
[全注意力层数, KV head 数, 最大位置数, 每个 head 的维度]
```

一个 head 可以先理解为模型内部的一组注意力计算；多组并行处理不同的信息。

每增加一个有效位置，对应的 K/V 容量是：

```text
2 × 全注意力层数 × KV head 数 × head 维度 × 每个元素的字节数
```

开头的 2 代表 K 和 V。本轮 KV 用 BF16，每个元素 2 字节。实际分配容量还要乘预分配的位置数。

代码见 [State](../tokenrush/state.py) 中的 `k`、`v` 和 `kv_bytes_per_token`。

</details>

### 3.3 这个模型还使用另一类记忆：循环状态

Swift Decode 使用的模型包含两类序列处理层。一类是刚才的全注意力层，另一类叫 **Gated DeltaNet**，代码里常缩写为 **GDN**。

先用动作理解它：每来一个新 token，就更新一张固定大小的“记忆矩阵”。

```text
处理完 P：   状态 S_P
再处理 A：   根据 S_P 和 A 算出 S_PA
再处理 B：   根据 S_PA 和 B 算出 S_PAB
```

`S_PAB` 表示“处理完 P、A、B 以后的状态”，下标只是帮助我们记住它对应哪段前文。

这种状态保存的是压缩后的历史信息。它的矩阵尺寸固定，不需要给每个旧 token 再增加一整行历史记录。模型通过门控决定遗忘多少旧信息，再根据当前输入修正记忆。

本项目用 FP32 保存这张循环矩阵。FP32 每个数 4 字节，通常比后面会讲的 BF16 保留更多有效精度，适合这里连续更新的计算。

模型同时包含全注意力层，所以整体仍有会随有效上下文增长的 KV 部分。

### 3.4 为什么这会影响投机解码

现在先想一个问题：已经算出了 `S_PABC`，后来发现最后一个 C 不该被接受，想回到 `S_PAB`。

对于按位置保存的 KV，我们可以重新界定哪些位置有效。对于一张已经被更新过的循环矩阵，仅仅把“长度减一”并不能让数值自动变回去。

因此，后面我们会保存几个阶段的矩阵快照。选择一个快照，就能选择一段已经确认的历史。这就是简历中“循环状态槽”的来由。

你现在只需记住两类状态的差别：

| 状态 | 直观理解 | 继续处理新 token 时 |
|---|---|---|
| KV Cache | 按历史位置保存的数值记录 | 写入新位置，读取有效前缀 |
| 循环矩阵 | 随输入不断更新的一张记忆矩阵 | 使用旧矩阵算出新矩阵 |

<details>
<summary>进阶阅读：Gated DeltaNet 怎样修正记忆</summary>

省略卷积、归一化和输出门，核心计算可以写为：

```text
S_decay = alpha × S_old
error   = v - kᵀ × S_decay
S_new   = S_decay + beta × outer(k, error)
output  = qᵀ × S_new
```

`q、k、v` 是当前输入形成的向量。`alpha` 控制旧状态的衰减，`beta` 控制更新强度。

理解第二行：先用 k 查询旧记忆，看它对当前 v 的预测是什么，再计算预测和当前 v 的差值。第三行把这个差值写回记忆，所以称为 Delta 更新。

`outer` 是外积：把两个向量组合成矩阵。本项目把状态矩阵按 `[key_dim, value_dim]` 存储。

Gated DeltaNet 还保存最近几个位置的卷积输入。仓库里使用长度为 16 的环形缓冲区，并限制投机深度，避免新写入覆盖仍需要的历史。第 7 课会把这些状态一起放回生成流程。

概念来源见 [Gated Delta Networks 论文](https://arxiv.org/abs/2412.06464)，实际计算见 [模型中的 gdn_forward](../tokenrush/model.py) 与 [Gated DeltaNet 融合内核](../tokenrush/fused.py)。

</details>

## 第 4 课：27B 模型怎样放进 32GB 显存

我们已经知道模型需要权重，也需要运行过程中不断更新的状态。先解决容量问题：这些东西能不能放进显卡。

### 4.1 先算最容易的一笔账

BF16 是一种浮点数格式，每个数占 2 字节。粗略把 270 亿个参数都按 BF16 存储：

```text
270 亿 × 2 字节 = 540 亿字节 ≈ 54GB
```

光这部分就超过了 32GB，还没有算 KV Cache、循环状态和中间结果。

所以本项目使用已经量化好的模型。**量化**就是用更少的位数近似表示原本的数值。

### 4.2 用一个小数演示 INT4

4 bit 能表示 16 种编码，可以把它们记成 0～15。一个字节有 8 bit，所以能装两个这样的编码。

编码本身还不是原始权重。我们还需要知道“编码对应多大的数”。项目使用的重建形式是：

```text
近似权重 = scale × 编码 + minimum
```

例如，使用一组**教学参数**：

```text
scale = 0.2
minimum = -1
```

那么：

| 编码 | 按这个规则恢复出的数 |
|---:|---:|
| 0 | -1.0 |
| 5 | 0.0 |
| 10 | 1.0 |
| 11 | 1.2 |
| 15 | 2.0 |

假如原权重是 1.13，使用最简单的就近选择，可以存编码 11，恢复成大约 1.2。这样省了存储，但引入了近似误差。

这个例子用十进制数演示量化网格，不追踪 scale 本身的浮点舍入。真正加载的目标模型已经离线完成了量化，我们不在本次实验里重新为它选择编码。

### 4.3 为什么要分组

不同区域的权重可能有不同的数值范围。让所有权重共用同一个 scale 和 minimum，未必能近似得好。

因此，本项目让**每 128 个权重共享一组 scale 和 minimum**。这就是模型名中 `g128` 的含义。

每组需要的空间为：

| 内容 | 大小 |
|---|---:|
| 128 个四位编码 | 64 字节 |
| 一个 BF16 scale | 2 字节 |
| 一个 BF16 minimum | 2 字节 |
| 合计 | 68 字节 |

所以平均每个权重并非恰好 4 bit，而是：

```text
68 × 8 / 128 = 4.25 bit
```

如果理想化地把 27B 个参数都按这个格式存储，约为 14.34GB。真实运行还包含未量化的张量、各种状态和工作缓冲区，所以最终显存要靠实际测量。

### 4.4 INT4 权重不等于所有计算都用 INT4

在本项目里，几种格式各有用途：

| 格式 | 每个数占用 | 本次常见用途 |
|---|---:|---|
| INT4 编码 | 半字节，另外有分组参数 | 主要大矩阵权重的打包存储 |
| BF16 | 2 字节 | 许多输入和输出激活、KV Cache |
| FP32 | 4 字节 | 循环矩阵状态、部分中间累加 |

读取 INT4 权重时，内核会根据编码、scale 和 minimum 恢复需要的数值，再参与计算。这一步叫**反量化**。

这就是简历里 INT4 的具体含义：重点是压缩权重的存储和读取。

### 4.5 装得下以后，还要减少搬运

假如每一步都这样做：

```text
读 INT4 权重 → 展开成完整 BF16 矩阵并写入显存 → 再读取这个矩阵做乘法
```

虽然长期保存的是压缩权重，中间仍然多了一大块数据的写入和读取。

项目的小行数 Triton 路径改为按块工作：读取当前需要的压缩权重块，在计算内核里恢复数值，直接参与乘法。多行验证时，同一块恢复后的权重还可以服务多个输入位置。

下一课会解释“内核”和“Triton”是什么。此处先理解目的：让为一个 token 搬运大量权重的成本尽量低。

<details>
<summary>进阶阅读：GPTQ、加载时量化和长 Prefill</summary>

目标模型使用发布好的 GPTQ checkpoint。本次没有重新执行目标模型的 GPTQ 校准或训练。

最简单的 round-to-nearest，简称 RTN，就是按量化网格就近取整。GPTQ 会使用校准输入，考虑线性层输出误差并进行量化误差补偿。本文的小数例子只用于理解格式和近似，不是完整 GPTQ 算法。

MTP 草稿模块在 checkpoint 中按 BF16 保存。实验适配层调用 `build_mtp(..., int4=True)` 时，会对它的若干线性层进行 RTN 量化。这与目标模型已经完成的离线 GPTQ 是两件事。第 6 课会说明 MTP 的作用。

长 Prefill 也有不同的计算选择：`QLinear` 对超过小行数范围的输入，可能先展开当前矩阵，再调用 `F.linear`。因此，短 Decode 内核的做法和收益不能直接套到所有输入长度。

格式和分派见 [quant.py](../tokenrush/quant.py)，目标模型原量化实现可在 [上游固定版本](https://github.com/zyhector/token-rush/blob/b592bc6d91f0ea925b6a0179cbe65d1362b96381/tokenrush/gptq.py) 中查阅。

</details>

## 第 5 课：一次 GPU 计算怎样变快

模型已经能放进显存了。接下来回到 P → A → B 的过程：每产生一个 token，CPU 和 GPU 分别在忙什么。

### 5.1 CPU 安排工作，GPU 执行数值计算

Python 程序运行在 CPU 一侧。它告诉 GPU 接下来要执行什么运算。一次提交给 GPU 的计算程序，通常叫一个 **kernel，计算内核**。

一个模型步骤可能包含很多内核：读取权重并做乘法、归一化、激活、写入缓存、选下一个 token，等等。

```text
CPU：准备和提交操作 1 → 准备和提交操作 2 → 准备和提交操作 3
GPU：       执行操作 1 →        执行操作 2 →        执行操作 3
```

这张图只表示职责和依赖；真实执行可以异步进行，CPU 提交和 GPU 执行并不总是整齐交替。

这里有两种可优化的成本：GPU 内部的数据读写和计算，以及 CPU 反复提交操作的开销。

### 5.2 PyTorch 和 Triton 分别负责什么

**PyTorch**负责张量、设备管理，以及调用各种运算。你可以把张量放到 GPU，并使用它提供的 CUDA Graph 接口。

**Triton**允许我们用接近 Python 的写法描述专门的 GPU 内核，再由它编译执行。在这个引擎里，它用于 INT4 矩阵运算，以及多个小操作的融合实现。

一个线性层的核心是矩阵乘法。下面用二维数字演示，数值是教学用的：

```text
输入 x = [2, 1]
两行权重分别是 [1, 3] 和 [-1, 2]

第一个输出 = 2×1  + 1×3 = 5
第二个输出 = 2×(-1) + 1×2 = 0
```

真实模型的向量和矩阵大得多，GPU 会把任务分成很多块处理。怎样分块、怎样让多个输入共用权重，是内核实现要考虑的事。

### 5.3 算子融合减少中间往返

假设某处需要先做残差相加，再做归一化。

**残差相加**就是把一层算出的变化量加回原来的向量。**归一化**根据这串数的整体大小调整尺度；项目里常见的是 RMSNorm。

分开执行时，大致是：

```text
kernel 1：相加，把结果写入显存
kernel 2：从显存读回结果，进行归一化
```

融合后，一个 kernel 可以在内部继续处理刚算出的中间值，减少部分中间读写，也少一次独立操作的启动。这叫 **算子融合**。

本项目的例子包括残差加 RMSNorm、MLP 中的激活与逐元素乘法，以及 Gated DeltaNet 的多个连续步骤。这里的 MLP 可以先理解成每层中用若干线性变换和激活函数进一步处理向量的模块。

### 5.4 CUDA Graph 保存的是执行步骤

生成 A 后、生成 B 后、生成 C 后，模型主体要做的许多操作顺序是重复的。

**CUDA Graph**可以先捕获这串 GPU 操作，后续通过一次图重放把它们再次提交，减少反复经过 Python、框架和驱动的调度开销。

```text
初始化时：预热 → 捕获一套解码步骤

生成时：
重放这套步骤，输入 A → 输出 B
重放这套步骤，输入 B → 输出 C
重放这套步骤，输入 C → 输出 X
```

图会重新做计算，输出由当前输入和状态决定。

### 5.5 输入每次不同，图怎样复用

关键是：**缓冲区的位置不变，里面的值可以变。**

可以把图里的两个输入缓冲区画成这样：

| 重放次数 | `tok` 这块缓冲区中的值 | `pos_t` 这块缓冲区中的值 |
|---:|---|---:|
| 第一次 | A 的编号 | 100 |
| 第二次 | B 的编号 | 101 |
| 第三次 | C 的编号 | 102 |

数字 100～102 是教学位置。每次 kernel 都从同一块显存读取当前值，所以它知道该处理哪个 token、写入哪个位置。

项目把当前 token、位置、接受数量等动态值放在长期存活的 GPU 张量中。代码中的 `tok`、`pos_t` 就是这些缓冲区。

### 5.6 现在再看 eager 和 graph

**eager**表示程序按通常方式逐步调用运算；**graph**表示使用捕获后的图重放。

本项目的两条路径都使用这个引擎的量化权重和优化算子。换成 graph，主要改变的是步骤的提交方式。

| 方式 | GPU 里有哪些计算 | CPU 怎样安排 |
|---|---|---|
| eager | 模型前向、更新状态、选择 token | 每步执行相应调用逻辑 |
| graph | 捕获好的模型步骤 | 每步重放计算图 |

因此 eager 已经是一个经过算子优化的引擎路径。它不是独立的 Hugging Face 模型基线。

### 5.7 两种优化可以一起用

算子融合减少操作数量和中间读写；CUDA Graph 减少反复安排这些操作的开销。图里仍然可能有许多 kernel。

在本项目中，我们同时使用这两种方式。捕获前要完成必要的编译和预热，再重置被预热改变的状态。正式生成时，图外仍要循环、取回输出并进行相应同步。

<details>
<summary>进阶阅读：读 Triton 内核前，先认四个概念</summary>

**输入行数。** 把输入写成 `X[M,D_in]`，权重写成 `W[D_out,D_in]`。普通解码的 M 通常为 1，后面的四位置验证则是 M=4。M 是同一序列中处理的位置数，不自动等于请求数。

**分块。** 权重太大，需要每次处理一块。多行 INT4 内核读入并反量化一个权重块后，用它服务多个输入行；使用 `tl.dot` 和 FP32 累加。内部会补齐行数并用掩码排除无效行，这些实现细节也有成本。

**Split-K。** 矩阵乘法需要把很多乘积相加。把这一长串求和分给多个程序，各自算部分和，叫 Split-K。这样增加并行工作，也增加部分结果的存储和合并。本项目某些后续融合算子能直接消费这些 FP32 部分和。这里的 K 是矩阵的归约维度，和草稿深度不是同一个 K。

**自动调优。** Triton 可以在一组候选分块、warp 数、流水线阶段数中选择配置，叫 autotune。输入形状不同，选到的配置也可能不同。第 8 课会看到，这给数值排查提供了线索。

对应实现见 [量化内核与分派](../tokenrush/quant.py)、[融合内核](../tokenrush/fused.py)。通用背景可读 [Triton 矩阵乘教程](https://triton-lang.org/main/getting-started/tutorials/03-matrix-multiplication.html) 和 [PyTorch CUDA Graph 文档](https://docs.pytorch.org/docs/2.14/notes/cuda.html#cuda-graphs)。

</details>

### 小练习：两种加速省的是什么

某次修改把“相加”和“归一化”放进同一个 kernel。另一次修改保留这些 kernel，但把整步捕获后重放。它们分别是什么优化？

<details>
<summary>展开答案与原因</summary>

第一种是算子融合，改变了操作组织和中间数据传递。第二种是 CUDA Graph，减少重复提交一串操作的调度开销。

两者可以组合使用。仅看最终总速度，无法直接分出每一种优化各省了多少时间。

</details>

## 第 6 课：让便宜的模块先猜三个 token

到目前为止，每次主模型计算都只为我们确认一个新 token。既然完整模型很大，能否少做几次这样的调用？

### 6.1 先提出一个办法

继续第 2 课的例子。我们已经显示了 A，普通生成后面三个 token 的过程是：

```text
主模型处理 A → 得到 B
主模型处理 B → 得到 C
主模型处理 C → 得到 X
```

现在让一个计算成本更低的模块先猜测 A 后面是什么。假设它猜：

```text
B、C、D
```

这些候选叫**草稿 token**。提出草稿的模块叫 **draft**，负责最终判断的主模型叫 **target**。下文主要使用“草稿”和“主模型”这两个中文名称。

接着让主模型检查这段草稿，接受开头正确的部分，并纠正第一个错误。这种方法叫 **Speculative Decoding，投机解码**。

### 6.2 主模型究竟检查了什么

先把输入和输出分开画。A 已经显示，但还没有被主模型当作输入处理。验证时，主模型读入：

```text
A、B、C、D
```

对于这四个连续位置，它分别计算“下一个应该是什么”：

| 本行输入 | 这一行实际在预测 | 教学预测结果 |
|---|---|---|
| A | P,A 后面的 token | B |
| B | P,A,B 后面的 token | C |
| C | P,A,B,C 后面的 token | X |
| D | P,A,B,C,D 后面的 token | 假设为 Y |

一行输入预测它的后继。因此，第一行拿到 B，第二行拿到 C，第三行拿到 X。

现在检查草稿：第一个 B 正确，第二个 C 正确，第三个 D 应该改为 X。

所以这一步可以确认的新输出是：

```text
B、C、X
```

加上之前已经显示的 A，回答变成：

```text
A、B、C、X
```

这里没有再次输出 A。它已经在 Prefill 结束时显示过了。

### 6.3 为什么第四行的 Y 不能拿来用

因为第四行是在错误前文 `P,A,B,C,D` 下预测的。正确回答应该走到 `P,A,B,C,X`，这已经是不同的前文。

所以一旦遇到第一个不匹配，后面在错误草稿前文下算出的预测就不再用于这轮输出。

这叫**接受连续匹配的前缀**。“前缀”就是从最开头开始的一段。

即使你看到比较结果是：

```text
第一个对，第二个错，第三个又碰巧对
```

也只能接受第一个，因为第三个已经建立在错误的第二个草稿上。

### 6.4 猜三个，为什么最多可以输出四个

还是沿着正确顺序 `A B C X`，并假设 X 后面的正确选择是 E。现在给草稿模块四种不同的猜法：

| 草稿猜测 | 连续猜对几个 | 本轮新输出 | 原因 |
|---|---:|---|---|
| Q R S | 0 | B | 第一项就错，主模型直接给出 B |
| B Q R | 1 | B C | 接受 B，再由主模型纠正为 C |
| B C D | 2 | B C X | 接受 B、C，再纠正为 X |
| B C X | 3 | B C X E | 都正确，最后一行还预测出了 E |

这个表暂不考虑达到输出长度后停止的情况，只看一步能确认多少输出。

最后一种情况中，主模型处理完 X 已经知道 E 可以作为下一项。这个额外获得的输出叫 **bonus token**。

因此，固定提出三个草稿时，一步可用的新输出数是：

```text
连续接受的草稿数 + 1
```

这个“加一”来自主模型自己的纠正预测，或者全部正确时的 bonus 预测。

### 6.5 多个位置一起算，为什么没有破坏自回归

因为草稿已经把候选输入给出了，主模型现在有了一段已知输入可以检查。

和 Prefill 一样，许多线性投影可以一起处理多行。但注意力仍然受因果约束：A 那一行不能借用后面的 B、C、D 来作弊。循环状态也仍然按 A、B、C、D 的位置顺序更新。

这四行属于**同一个请求的四个连续位置**。本次同时只处理一个请求，所以请求的批大小（batch size）仍是 1。

接受第一个草稿之后，它才成为正确前文的一部分；继续接受后面草稿时，前面的条件也已经被确认。因此，正确的验证和状态处理能沿着主模型的选择继续生成。实际实现还要检查不同形状的浮点计算是否改变了选择，第 8 课会讲我们碰到的情况。

### 6.6 这个项目由谁生成草稿

本项目使用模型自带的 **MTP 预测头**。MTP 全称是 **Multi-Token Prediction，多 token 预测**。这里的“头”就是附加在模型体系中的一个较小预测模块。

Speculative Decoding 是这套“提出候选再验证”的生成方法；MTP 是本项目用于提出候选的具体模块。

它使用两份信息：

```text
已经确定的下一个 token，例如 A 的 embedding
                     +
主模型刚处理完 P 时得到的最终 hidden
```

它把这两份信息组合起来，通过较小的注意力和 MLP 模块，预测 A 后面的 B。

然后，同一个预测头继续用自己的中间表示，猜 B 后面的 C、C 后面的 D：

```text
主模型 hidden + A → 草稿 B
草稿模块 hidden + B → 草稿 C
草稿模块 hidden + C → 草稿 D
```

后两次还没有真实的未来主模型 hidden，所以这些猜测可能逐渐不准。它们最终都要经过主模型验证。

**深度 3**表示一轮串联提出三个草稿。使用的是同一个草稿头，不需要三个独立的完整模型。本次也没有下载额外的 DFlash 草稿模型。

<details>
<summary>想对照 MTP 代码：两份输入如何组合</summary>

在 [mtp.py](../tokenrush/mtp.py) 中，先分别归一化 token 的 embedding 和主模型 hidden，再拼接起来。原本两个长度为 hidden 的向量，组合成两倍长度，通过 `fc` 投影回一个 hidden 宽度。

之后经过一个包含注意力和 MLP 的模块，再归一化并做词表预测。它有自己的注意力缓存，embedding 和输出层参数来自主模型。

草稿侧可以只使用输出层的一部分词表行。本轮上限是前 131072 个 token，用来减少草稿侧工作量；主模型的最终验证仍然使用完整词表。词表外的 token 仍可以作为纠正或 bonus 输出。

主模型验证后，会得到真实的各位置 hidden。下一轮先用确认过的 token 和这些 hidden 校正草稿侧历史，再继续猜。这样不会把草稿自己猜出的中间表示一直当成真实主模型状态。

</details>

### 6.7 少调用主模型，不等于一定更快

下面是**教学时间**，用于理解成本，不是 GPU 实测：

```text
普通一步：10ms，产生一个新 token
普通三步：30ms，产生 B、C、X

投机一步：
  提出三个草稿 6ms
  主模型验证 13ms
  处理状态和输出 1ms
  合计 20ms，产生 B、C、X
```

在这个例子里，生成相同三个新 token，时间从 30ms 降到 20ms，速度是原来的 1.5 倍。

为什么验证四个位置可能不需要普通四步那么长？第 4、5 课已经给出了原因：许多投影可以让一次权重读取服务多行输入，调度也可以一起组织。

不过多行计算、草稿本身和状态处理仍有额外成本。如果同样花了 20ms，却因为草稿很差只输出一个新 token，就比普通的 10ms 一步更慢。

### 6.8 接受率怎样变成平均输出数

再看一笔教学小账。假设运行十轮，每轮提出三个草稿：

```text
总草稿数：10 × 3 = 30
总接受数：18
接受率：18 / 30 = 60%
```

每轮还有一个来自主模型的纠正或 bonus 输出，所以十轮共得到：

```text
18 个接受草稿 + 10 个主模型输出 = 28 个新 token
平均每轮：28 / 10 = 2.8 个
```

把这个过程写成公式，就是固定草稿数 K 时：

```text
平均每轮可用新输出 = 1 + K × 接受率
```

这个结果还没有扣除最后一轮超出目标长度的尾部。它也不是速度倍数，因为一轮投机步骤通常比普通一步贵。第 9 课会用真正的计时数据来计算速度。

### 小练习：这一步应该返回什么

已经显示 A。草稿是 `B、Q、R`，主模型前两行的预测分别为 `B、C`。本轮新增输出是什么？之前的 A 要不要再返回一次？

<details>
<summary>展开答案与原因</summary>

新增输出是 B、C。第一个草稿 B 正确，第二个 Q 应纠正成 C；后面的 R 不再使用。

A 已经显示过，所以不再返回。当前回答变成 A、B、C，下一轮等待主模型处理的是 C。

</details>

## 第 7 课：猜错以后，怎样回到正确状态

第 6 课确定了输出规则。现在检查模型内部：验证过错误的 D 后，怎样保证下一轮从正确的 C 后面继续？

### 7.1 先把“显示”和“处理”重新对齐

使用贯穿全文的情况：

```text
之前已显示：A
草稿猜测：B、C、D
本轮确认的新输出：B、C、X
```

用户此时看到 A、B、C、X。主模型应该保留的状态是：

```text
处理完 P、A、B、C 之后的状态
```

为什么不包括 X？因为 X 是处理完 C 后刚预测出来的。它还没有作为输入被处理。

也不能保留处理完 D 的状态，因为 D 被拒绝了。

### 7.2 用真实位置的形式手算一次

位置编号从 0 开始。假设 P 占据 0～99，A 在位置 100：

| 位置 | 验证时临时放入的 token | 本轮结束后怎样处理 |
|---:|---|---|
| 100 | A | 处理结果有效 |
| 101 | B | 草稿接受，处理结果有效 |
| 102 | C | 草稿接受，处理结果有效 |
| 103 | D | 草稿拒绝，结果不能进入有效历史 |

这次接受两个草稿，总共有效处理了 A、B、C 三个输入。所以“下一个待处理位置”从 100 前进到 103。

在位置 103 等待下一轮输入的，应当是刚预测出来的 X。

```text
位置增加量 = 1 个已经确定的输入 A + 2 个接受草稿 = 3
```

如果你只加了接受数 2，就少算了 A；如果加了全部验证行数 4，就错误地把 D 算了进去。

### 7.3 KV Cache 怎样处理被拒绝的位置

验证时，位置 103 可能已经写入 D 的 K/V。引擎不必立刻把这块内存擦成零。

它先把逻辑上的有效前缀保留到位置 102。下一步处理 X 时，重写位置 103 对应的 K/V，然后按新的有效范围读取历史。

这依赖一个前提：读取严格遵守当前位置和因果范围。物理内存里暂时存在旧值，不等于模型允许读取它。

### 7.4 循环矩阵怎样选择正确版本

循环矩阵已经被每个候选位置更新过。因此，验证时为各个前缀保存一份快照：

| 状态槽 | 保存什么 |
|---:|---|
| slot 0 | 处理完 P、A 的状态 |
| slot 1 | 处理完 P、A、B 的状态 |
| slot 2 | 处理完 P、A、B、C 的状态 |
| slot 3 | 处理完 P、A、B、C、D 的临时状态 |

本轮接受两个草稿，所以选择 slot 2。后续计算就从处理完 C 的状态继续。

**slot 是槽位编号，也就是保存快照的格子编号。** 选择 slot 2 的动作，在代码里叫提交状态。

这里无需对矩阵计算做逆运算。我们已经存好了对应的正确版本。

### 7.5 把所有分支归纳为同一条规则

把这一轮开头已经显示的输入叫 `c`，三个草稿叫 `d1、d2、d3`。这只是为了写出适用于任意 token 的表；在刚才的例子里，它们是 A、B、C、D。

| 连续接受草稿数 n | 有效处理的输入 | 位置增加量 | 选择哪个槽 |
|---:|---|---:|---:|
| 0 | c | 1 | slot 0 |
| 1 | c、d1 | 2 | slot 1 |
| 2 | c、d1、d2 | 3 | slot 2 |
| 3 | c、d1、d2、d3 | 4 | slot 3 |

因此：

```text
新位置 = 原位置 + n + 1
新槽位 = n
下一轮待处理 token = 本轮最后一个主模型纠正或 bonus 输出
```

### 7.6 接受数会变，怎样放进 CUDA Graph

固定深度为 3 时，主模型验证的输入形状始终是四行。变的是接受数量。

项目把比较、计算接受数和选择结果都留在 GPU 上做。比如：

```text
逐项是否匹配：  [1, 0, 1]
从头累计乘积：  [1, 0, 0]
把结果相加：    1
```

累计乘积叫 `cumprod`。遇到第一个 0 后，后面的结果都变为 0，因此正好数出连续匹配的前缀长度。

接受数保存在 GPU 张量 `n_accepted` 中。再根据它选择主模型的纠正或 bonus token、更新位置、选择状态槽，就能让图的执行结构保持固定，而每轮数据不同。

这个投机图里包含草稿生成、主模型验证和状态更新。图外仍然需要读取接受数和新输出，并继续生成循环。

### 7.7 还有两份历史也要照顾

一份是第 3 课提到的短卷积历史。它保存在环形缓冲区里，通过位置、容量约束和后续覆盖来保证有效历史仍可读取。

另一份是草稿头自己的注意力缓存。草稿生成时，后续位置用的是预测头自己的 hidden；主模型验证后，已经拿到了真实 hidden。下一轮会重新对齐相关草稿历史，再继续预测。

所以排查状态错误时，要同时想到：KV、循环矩阵、卷积历史、草稿侧历史，以及它们的位置。

### 小练习：接受一个草稿时，槽位为什么是 1

验证输入是 `A、B、Q、R`，只接受 B，然后主模型纠正为 C。开始位置是 100。请写出新输出、新位置、有效循环状态和槽位。

## 第 8 课：一起重走这次输出分叉的排查过程

前面的 A、B、C、X 都是教学例子。这一课开始使用真实实验现象。

我们已经知道正确的投机算法怎样工作。接下来要回答：代码运行出来，为什么仍然可能和普通路径选出不同 token？

### 8.1 先把现象说准确

第一次检查三种方式是否生成相同内容时，程序发现：

```text
eager 与 CUDA Graph：输出相同。
投机解码：与它们不同。
每种方式各自重复三轮：都能重现自己的输出。
```

这个生成一致性检查在程序里叫 **gate**，可以理解成正式性能对照之前的一道检查关卡。

英文输入的第 21 个输出 token 开始不同；程序从 0 编号，所以记录为 `first_difference=20`。代码和中文输入的首次不同位置分别记录为 61 和 69。

**分叉**就是从某个位置开始，两条生成路径选出了不同 token。之后的前文不同，后续回答可能越来越不一样。因此应优先研究第一个分叉位置。

### 8.2 先列出几个可以验证的解释

| 可能解释 | 可以做什么检查 |
|---|---|
| 输出收集错位，把 A 又输出了一遍 | 对照实际返回 token 和本轮主模型选词 |
| 位置或槽位更新错误 | 检查接受数、位置增量、当前输入和槽位 |
| 相同状态下的数值计算不同 | 固定输入和状态，对照中间结果 |

先做前两项，因为它们能直接验证第 6、7 课的收集与提交规则。

结果是：实际返回的 token 确实对应本轮主模型的选择；当前位置和槽位的计数也对得上。

这一步排除了当次记录中明显的输出收集与计数问题。第 3 课的小练习提醒过我们：计数相同还需要继续检查状态中的数值。

### 8.3 用 logits 解释“它为什么选了另一个词”

英文分叉处，两个关键候选的真实分数是：

| 候选 | token ID | 普通图路径 | 投机验证路径 |
|---|---:|---:|---:|
| ` executed` | 15234 | 21.75 | 21.625 |
| ` granted` | 11340 | 21.625 | 21.625 |

普通图路径中，executed 的分数更高，所以选它。

投机路径里两者打平；该次 `argmax` 选择了编号更靠前的 granted。查看候选列表的打印顺序不能代替查看真正的 `argmax` 结果。

两条路径的最大 logits 绝对差只有 0.125，但足以改变第一名。这里已经能解释选词行为：程序确实按照各自算出的分数选择了 token。

下一步应当查“为什么分数变了”。

### 8.4 固定 hidden，单独检查输出层

第 1 课画过这条线：

```text
hidden → lm_head → logits → token
```

现在 logits 不同，可能是 hidden 已经不同，也可能是相同 hidden 经过不同的输出层执行方式后才变得不同。

当时还发现，输出层在单行和四行输入时选用了不同的 Triton 调优配置。这使它成为一个值得检查的位置。

为了分清原因，我们把同一份 hidden 保存下来，保持它不变，再做几种投影：

```text
同一份 hidden → 单行输出层
同一份 hidden → 四行输出层
同一份 hidden → 统一调优配置的输出层
```

“冻结 hidden”就是这个意思：固定这次对照中的输入数组，不让上游计算变化干扰当前实验。

对捕获到的这些输入，三种输出层计算得到的 logits 全部逐值相同。但普通路径和投机路径实际送入输出层的 hidden，5120 个元素中已经有 4359 个不同。

因此，这次差异已经发生在输出层之前。下一步应继续向前追踪。

这个结论针对当次固定输入的实验；如果换了其他输入，仍然需要相应验证。配置不同本身只是一条线索。

### 8.5 从同一个起点，比较“一次四行”和“连续四次一行”

现在准备两份完全相同的起始状态，给它们完全相同的四个输入 token：

```text
起点状态 S + 四个输入 → 连续做四次单行计算
起点状态 S + 四个输入 → 一次处理四行
```

这里的 S 包括有效 KV、循环矩阵、卷积历史和位置。Prefill 后的对应状态也先做了比较，确认相同。

然后在模型内部各个算子之后记录数值。这就叫**算子回放和追踪**：重做相同输入的计算，观察从哪一步开始出现差异。

这样做的理由是：如果起点已经不同，后面算出不同结果就无法说明当前算子有问题。固定同一起点，才能研究计算方式本身的影响。

### 8.6 找到最早观察到的差异，再做控制实验

在被追踪的第一个验证块中，第 0 层的 Gated DeltaNet 输出已经有一个值不同：6144 个值中有 1 个不同，最大绝对差约为 `0.0000000298`，也就是 `2.98e-8`。

此时最终选出的 token 仍然相同。中间数值开始变化的时间，可以早于最终 token 分叉的时间。

接着我们每次恢复同一份初始状态，只改变指定设置，做了四组对照：

| 设置 | 1365 处观测中出现差异的数量 |
|---|---:|
| 原来的设置 | 1246 |
| 只统一 Gated DeltaNet 的分块 | 0 |
| 只统一量化投影的调优配置 | 1246 |
| 两项都统一 | 0 |

这里的一处“观测”是追踪工具记录的一次中间结果比较，不是一个独立请求。

这些对照是在已有一致性设置基础上进行的，其中单 token 已经使用多行量化内核。表中只进一步改变标出的因素。

读表的方法是：只统一 Gated DeltaNet 分块就消除了该块中的全部观测差异；单独统一量化投影配置没有达到这个效果。因此，前者给出了有证据支持的修正方向。

后面各层也可能独立产生新的舍入差异，所以不能把所有 1246 处差异都断言为第一个小差值的传播。

### 8.7 “统一分块”到底改了什么

先想一组有 128 个数的向量。可以由一个程序处理完整 128 个数，也可以拆成两份，每个程序处理 64 个数。

本次 Gated DeltaNet 的一个 value head 就有 128 维。原来的内核策略大致是：

```text
输入少于四行：每个程序处理完整 128 维。
输入达到四行：拆成两个 64 维部分处理。
```

控制每个程序处理多少 value 维度的参数，叫 `BV`。

完整 head 路径还会在同一个 kernel 内做后续门控归一化；拆分路径则写出中间结果，再启动另一个 kernel 做归一化。

两个实现保留了相同的数学目标，但分块、编译布局和运算路径可能改变有限精度下的舍入结果。浮点计算不会因为数学公式相同，就自动逐位相同。

修正是在一致性模式下，把两边都设为完整 head 路径。代码里的核心设置是：

```python
self.gdn_bv = cfg.gdn_v_dim if consistent else None
```

`cfg.gdn_v_dim` 就是模型配置中的完整 value head 维度。`consistent=True` 表示启用这套显式的一致性执行设置。

注意，这里的 128 是网络里一个 value head 的宽度，和第 4 课每 128 个权重一组的量化分组，是不同的概念。

### 8.8 从局部修正回到完整回答

局部控制实验让我们知道怎样修改，但还要重新生成完整回答，确认输出收集、真实状态提交和后续步骤都正常。

修正后，三条输入、三种方式、各三轮的完整 128-token 生成通过了 gate。后续又让正式计时使用相同一致性策略，得到第 9 课的配对性能结果。

完整历史见 [MTP 诊断记录](../experiments/MTP_DIAGNOSTICS.md)。那里保留了阶段性判断和命令；读到本课后再去看它，各次诊断的目的会更清楚。

## 第 9 课：怎样证明加速结果有意义

现在假设你拿到两份记录：一种方法每秒生成 90 个 token，另一种每秒生成 180 个。能马上说“优化成功，快了两倍”吗？

先检查两件事：它们是否在完成同一个任务，以及时间是否按同一种方式计算。

### 9.1 先确认生成的是同一份回答

本项目先运行 gate，再运行 benchmark。**Benchmark 就是在约定条件下进行性能测量。**

Gate 的做法是：给三种执行方式相同的输入，要求生成相同长度的回答，再逐个比较 token ID。同一句话“意思差不多”，不足以通过这个检查。

每条输入以 CUDA Graph 第 0 轮的结果为参考，比较 eager、graph、mtp 的所有测量轮次。先确认输入 token 一样，再确认完整输出 token 一样。

这能回答：“这几条输入上，我们的优化执行方式是否保留了普通图路径的贪心输出？”

### 9.2 正确性检查和计时必须用同一套执行设置

项目里实际遇到过一次教训：`gate-002` 通过了，但随后 `bench-001` 的投机输出仍然分叉。

原因在于，当时 gate 使用了一致性执行设置，benchmark 则使用正常性能路径。通过检查的计算方式，与真正计时的计算方式没有完全对齐。

因此，后来新增了下面这个选项：

```text
--bench-kernels consistent
```

它让 benchmark 也采用对应的一致性策略，包括单 token 的量化计算路径、Gated DeltaNet 的分块和主模型状态槽数量。

最终的检查关系是：

```text
gate 的三种方式生成相同输出
              ↓ 使用匹配的执行设置
benchmark 的三种方式也生成相同输出
              ↓ 再与保存的 gate 回答比较
benchmark 的输出与 gate 参考相同
```

正式计时仍然保存输出并重新比较。这样，性能结论对应的是计时当时实际完成的计算。

<details>
<summary>进阶：为什么连状态槽数量、源码和进程都要记录</summary>

本轮三种方式都设置 `consistent=True, max_spec=3`，给主模型准备四个循环状态槽。普通解码虽然一次只处理一个新输入，也采用同样的槽配置。

这除了影响显存，还可能影响执行分支：引擎会用输入长度与槽数量的关系，决定短输入能否走某些融合路径。因此，“都是同一模型”还不足以说明内部执行条件相同。

三种方式各在独立进程中运行，减少前一种方式的显存分配和进程内设置对下一种方式的影响。例如，量化模块中让单行采用多行 kernel 的设置是进程内状态。

实验还记录配置、运行环境、源码指纹和源码快照。**指纹**可以理解为文件或配置计算出的摘要：相关内容变了，摘要通常也会变，便于发现两次运行是否用了不同代码。

权重清单中的文件名、大小和修改时间是来源记录的一部分；它们不能替代对全部权重文件内容做校验。查看证据时要分清记录到底覆盖了什么。

具体实现见 [numerics.py](../experiments/numerics.py)、[provenance.py](../experiments/provenance.py) 和 [一致性计时说明](../experiments/CONSISTENT_BENCH.md)。

</details>

### 9.3 用三个时间点算清速度

下面是**教学时间线，不是实际测量值**。假设一次回答固定输出 128 个 token：

```text
0.000 秒                    0.400 秒                       1.035 秒
   │                           │                              │
开始处理请求                 第一个 token 就绪               第 128 个 token 就绪
   └────── 首 token 时间 ──────┘
                               └──── 后续 127 个 token ───────┘
```

第一段时间是 **TTFT，Time To First Token，首 token 时间**：

```text
TTFT = 0.400 - 0.000 = 0.400 秒
```

第二段是后续解码时间：

```text
decode 时间 = 1.035 - 0.400 = 0.635 秒
decode 速度 = 127 / 0.635 = 200 token/s
```

分子为什么是 127？因为第一个 token 已经在第一段时间中产生，第二段只负责剩下的 127 个。

如果计算包含第一个 token 的整段生成速度，则是：

```text
整段生成速度 = 128 / 1.035 ≈ 123.67 token/s
```

同一次请求可以同时有“解码 200 token/s”和“整段生成 123.67 token/s”这两个结果，二者衡量的时间范围不同。

还有一个常见指标叫 **TPOT，Time Per Output Token**。这里按首 token 之后的平均时间计算：

```text
TPOT = 0.635 / 127 = 0.005 秒 = 5 毫秒
```

这是平均数。投机解码一次可能返回一批 token，因此不能据此声称用户每隔恰好 5 毫秒收到一个 token。

### 9.4 时间从哪里开始，哪些工作算进去

本实验使用 CPU 侧时钟，并在计时边界等待 GPU 完成。否则，CPU 可能只是刚刚提交了任务，GPU 还没算完，计时就结束了。

| 工作 | 是否计入本实验的生成时间 |
|---|---|
| 加载权重、编译 kernel、捕获 CUDA Graph | 不计入，提前完成 |
| tokenizer 把文字转成 token ID | 不计入，提前完成 |
| 状态重置、prefill、对应的草稿准备 | 计入首 token 时间 |
| 后续生成、读取输出 token、每步同步 | 计入后续解码时间 |
| 网络传输与服务排队 | 本轮实验没有这两个环节 |

这是一个模型执行实验。它给出的首 token 时间，不等同于包含网络、排队等开销的在线服务首字延迟。

还有一个容易把速度算高的地方：最后一步投机解码算出了四个可用 token，但距离规定的 128 个输出只差一个。这时，只把实际留下的一个计入输出数量，却保留整步计算耗时。不能把丢掉的三个尾部 token 也算成已经交付的输出。

你可以在 [measurement.py](../experiments/measurement.py) 中看到这些计数和时间边界。

### 9.5 这次真实实验用了哪些条件

现在从教学时间线回到项目真实记录。

| 条件 | 本次取值 |
|---|---|
| GPU | 单张 RTX 5090，32GB |
| 模型 | Qwen3.8-27B-TokenRush-int4g128 |
| 权重与缓存 | INT4 权重，BF16 KV cache，Triton 后端 |
| 请求方式 | 单请求，batch size 1 |
| 投机设置 | 每步提出 3 个草稿，使用一致性执行设置 |
| 输入 | 英文、代码、中文各一条 |
| 输出 | 贪心生成；关闭 thinking；忽略 EOS，固定输出 128 token |
| 重复方式 | 每种方式、每条输入预热 2 轮，再测量 3 轮 |

**EOS** 是表示回答结束的特殊 token。本实验忽略它，是为了让三种方式按固定长度接受比较；实际聊天通常需要根据结束标记停止。

一共测量：

```text
3 种方式 × 3 条输入 × 3 轮 = 27 个请求
```

本轮内部的逐 token 比较 27/27 通过；同一批结果再与保存的 gate 参考比较，也是 27/27 通过。这是同一批 27 个请求接受两种检查。

### 9.6 怎样读最终性能表

下表每个速度都是对应三轮的中位数，单位是 **首 token 之后的实际输出 token/s**。

| 输入 | eager | CUDA Graph | 投机解码 | 投机 / Graph | 草稿接受率 |
|---|---:|---:|---:|---:|---:|
| 英文 | 66.37 | 88.88 | 177.54 | 2.00× | 48.72% |
| 代码 | 59.72 | 88.88 | 200.56 | 2.26× | 60.87% |
| 中文 | 53.67 | 88.81 | 188.30 | 2.12× | 53.06% |

先读代码输入这一行：普通图路径约 88.88 token/s，投机路径约 200.56 token/s，后者是前者的约 2.26 倍。

草稿接受率 60.87% 表示提出的草稿中约六成通过验证。按第 6 课的公式，末步截断前每步平均可用输出约为：

```text
1 + 3 × 0.6087 ≈ 2.83 个 token
```

但加速比是 2.26，并非 2.83。生成草稿、验证多行和处理状态都要花时间。

这次最有依据的表述是：**在这三条输入、固定 128-token 输出的实验中，投机解码与普通图路径的输出相同，后续解码速度为后者的 2.00～2.26 倍。**

### 9.7 首 token 和显存也要一起看

下面的范围是“三条输入各自中位数”的最小值到最大值：

| 指标 | CUDA Graph | 投机解码 |
|---|---:|---:|
| 首 token 时间 | 370.5～387.6 ms | 380.6～394.7 ms |
| 包含首 token 的整段生成速度 | 70.47～71.11 token/s | 115.14～125.61 token/s |
| PyTorch 峰值 allocated 显存 | 16.549 GiB | 17.113～17.114 GiB |

投机解码把后续回答生成得更快，但本轮首 token 时间没有随之减半。它还需要保存草稿模块和额外状态，所以占用更多显存。

**Allocated** 是 PyTorch 分配给活跃张量等对象的内存统计；**reserved** 是它的显存分配器已经保留的内存池，可能包含暂时空闲的部分。二者都不等同于整张显卡所有进程的占用。

GiB 按 `2^30` 字节计算，GB 按 `10^9` 字节计算。看模型文件大小和运行显存时，先确认单位与统计对象。

### 9.8 这组实验能回答哪些问题

它已经回答了：这个配置能在单卡运行；这组输入上三种执行方式输出一致；一致性设置下投机解码有可测量的收益。

其他问题需要其他实验。例如，想知道量化是否损害生成质量，需要独立的精度或任务评估；想知道服务多个用户的能力，需要多请求实验；想判断长上下文是否同样受益，需要增加相应输入。

eager 的三轮波动也较大，例如中文输入约为 51.16～68.38 token/s。因此，本轮 graph 与 eager 的速度差，不能全部解释成已经测准的 CPU 提交开销。若要回答各部分耗时占比，还需要专门的性能追踪。

完整结果和配置保存在 [bench-002 报告](../reports/rtx5090-2026-10-03/bench-002.md)。当前证据是 INT4 模型内部执行路径的对照，没有运行独立的 Hugging Face / BF16 原模型作为正确性参考。

### 小练习：这个“200 token/s”算对了吗

某次请求输出 128 个 token，首 token 用了 0.4 秒，随后用了 0.635 秒。有人用 `128 / 0.635` 计算解码速度，并说用户整个请求都达到了这个速度。应该怎样改？

<details>
<summary>展开答案与原因</summary>

首 token 已经属于前 0.4 秒，后续解码的分子应为 127，所以解码速度是 `127 / 0.635 = 200 token/s`。

整段生成则用 `128 / (0.4 + 0.635) ≈ 123.67 token/s`。这两个指标都可以报告，但必须说明时间范围。

</details>

## 第 10 课：带着已经理解的例子读代码

你现在已经能手算 A、B、C、X 的生成过程。接下来读代码时，每次带着一个具体问题进去，会比从第一行连续读到最后一行容易得多。

### 10.1 第一个 A 是谁返回的

先打开 [experiments/gpu.py](../experiments/gpu.py)，找到 `Adapter.prime()`。

**Adapter** 在这里就是一层连接代码：把引擎不同的执行接口，整理成实验工具都能调用的 `prime()` 和 `step()`。

`prime()` 负责请求开始时的准备，并返回第一个输出 token。普通路径的主要顺序是：

```text
重置历史状态
     ↓
对整个输入 P 做 prefill
     ↓
取最后一个位置的 logits，选出 A
     ↓
把 A 放入下次调用要读取的位置，并返回 A
```

这时 P 已经处理完，A 已经输出。A 将作为下一步的输入。

投机路径会调用 `prime_spec()`，额外准备草稿模块的历史信息；它同样把第一个输出交回给实验工具。

### 10.2 接下来一个或一批 token 是谁返回的

继续看同一文件的 `Adapter.step()`。

| 方式 | 主要调用 | 一次交给实验工具的输出 |
|---|---|---|
| eager | `engine.decode()` 后选最高分 | 一个新 token |
| graph | `engine.step()` | 一个新 token |
| mtp | `engine.spec_step()` 后收集结果 | 接受的草稿，再加一个主模型 token |

投机分支里最值得亲手对照的表达式是：

```python
engine.drafts[:n].tolist() + [int(engine.tok[0])]
```

代入我们熟悉的例子：

```text
drafts = [B, C, D]
n = 2
engine.tok[0] = X

drafts[:2] + [X] = [B, C, X]
```

A 不在这次结果里，因为 `prime()` 或前一次 `step()` 已经输出过它。这一行直接对应第 6 课的“接受草稿，再补一个主模型结果”。

### 10.3 下一步应该从哪里继续，看哪个状态

接着打开 [tokenrush/model.py](../tokenrush/model.py)，按名称找到这几处：

| 位置 | 带着什么问题读 |
|---|---|
| `Engine._spec_step()` | 草稿怎样提出，验证结果怎样得到接受数？ |
| `Engine._verify_step()` | 四行输入怎样使用历史，保存哪些中间结果？ |
| `Engine.capture_spec()` | 哪段 GPU 工作被捕获，哪些缓冲区要反复使用？ |
| `Engine.spec_step()` | 图重放后，CPU 怎样取得接受数并更新自身记录？ |

读到位置变化时，重新画第 7 课那张表：起点位置 100，接受两个草稿，最后应当是位置 103、slot 2、下一次输入 X。

再打开 [tokenrush/state.py](../tokenrush/state.py)，把表里的对象与实际缓冲区对上：KV、循环矩阵、卷积历史、当前位置，以及选中的状态槽。

这样你是在检查一条完整的状态变化过程，而不是孤立记住变量名。

### 10.4 真正的模型计算在哪一层

`Engine._body()` 组织模型的逐层计算。读它时，可以先用下面的简图定位：

```text
token ID → embedding
               ↓
       多层模型计算，每层大致包含：
       归一化 → Attention 或 Gated DeltaNet → 残差相加

               ↓

               ↓

               ↓ lm_head

```

Attention 与 Gated DeltaNet 的历史保存方式不同，第 3 课已经分别讲过。归一化、残差和 MLP 的作用在第 5 课。这里把它们重新放回同一条计算链。

## 面试练习：先讲一个完整故事，再回答追问

这一节适合学完正文后练习表达。第一次阅读可以先跳过；能自己解释的内容，面试时才容易应对变化后的问题。

### 30 秒介绍：目标、做法、结果

> 我做的 Swift Decode 是一个单卡大模型推理项目，在 RTX 5090 32GB 上运行 27B INT4 模型。我主要完成了三种执行方式的实验对照、投机解码输出分叉的诊断，以及一致性执行设置的修正。修正后，在三条输入、固定 128-token 输出的测试中，投机解码与普通 CUDA Graph 路径逐 token 一致，后续解码速度达到约 178～201 token/s，是普通图路径的 2.00～2.26 倍。

先把这个版本讲顺。对方追问实现，再展开下一个版本中的对应部分。

### 两分钟介绍：加速思路、工程难点、验证

> 项目的目标是在一张 32GB 显卡上跑通 27B 模型，并加快单个请求的生成。权重使用 INT4 压缩；执行中用 Triton 做量化矩阵运算和算子融合，再用 CUDA Graph 重放每步 GPU 工作。
>
> 更进一步的加速来自投机解码。一个较轻的 MTP 模块先猜三个 token，主模型一次检查这些候选，从头接受连续正确的部分，并补一个主模型自己的输出。接受得多时，一次主模型调用就能推进多个 token。
>
> 工程上有两个需要分清的地方。一个是状态：最新输出的 token 还要在下一步作为输入，所以接受两个草稿时，输出三个新 token，但要选的是处理完第二个草稿后的循环状态。另一个是数值一致性：逐 token 与四行验证虽然对应同一套数学计算，实际分块不同也可能改变浮点结果。
>
> 我遇到过三种方式各自重复稳定，但投机输出与普通路径不一致的问题。我先核对输出收集和位置计数，再固定 hidden 检查输出层，最后恢复相同历史状态，追踪逐 token 与四行计算的中间差异。控制实验表明，在那个验证块里统一 Gated DeltaNet 的分块能消除全部观测差异，于是把完整 head 分块接入一致性设置。
>
> 最后重新做完整输出检查，并让性能测量采用匹配设置。三条输入各测三轮，投机与普通图路径的输出一致，解码速度提高到后者的约 2.00～2.26 倍。我也分别记录了首 token 时间和显存，避免把解码收益当成整个请求的同等收益。

### 练习一：基础与显存（对应第 1～4 课）

**Q01：这个项目具体想解决什么问题？**

在单张 32GB GPU 上运行 27B 模型，并缩短单个请求的生成时间。先通过 INT4 降低权重体积，再优化执行和解码方式；用相同输入、相同输出条件下的实测判断收益。

**Q02：Token、logits、hidden 分别是什么？**

Token 是被编号的文本片段；logits 是模型给各候选的分数；hidden 是模型内部用于产生这些分数的向量。排查不同输出时，可以从 token 追到 logits，再追到 hidden，逐步缩小范围。

**Q03：Prefill 和 decode 有什么区别？**

Prefill 处理已经知道的整段输入，并给出第一份输出分数。Decode 再把最新生成的 token 当作输入，继续产生后继；这时新的输入要等前一步选出来，通常每步只有很少的行。

**Q04：已经输出 A，模型就已经处理完 A 了吗？**

在本文的生成循环里，还没有。处理 P 时选出了 A，A 会在下一步被送入模型，产生 B。这个时间上的差别决定了位置计数，也决定投机验证后应该保留哪个状态。

**Q05：KV cache 节省的是什么？**

它保存已处理 token 的 K、V，避免每一步重复计算它们。新位置仍然要访问所需的历史 KV，所以缓存能省重复计算，却不会让全部历史读取成本消失。

**Q06：为什么除了 KV，还要管理循环状态？**

这个模型既有 attention 层，也有 Gated DeltaNet 层。前者按位置保存 KV，后者不断更新固定大小的记忆矩阵；拒绝草稿后，需要分别恢复到相同的有效前缀。

**Q07：27B 模型为什么通常不能直接以 BF16 权重放进 32GB？**

约 270 亿个参数，每个两字节，仅权重就是约 54GB，还没有计入缓存和工作空间。INT4 减少每个权重的存储，但实际显存还包括分组参数、未量化部分和运行状态。

**Q08：int4g128 中的 128 是什么？**

每 128 个权重共用一组量化参数。按这里的存储格式，128 个四位编码占 64 字节，再加 BF16 的 scale 和 minimum 共 4 字节，合计 68 字节。平均是 4.25 bit/weight，而不只是 4 bit。

### 练习二：GPU 执行（对应第 4～5 课）

**Q09：INT4 模型是否从头到尾都在做整数运算？**

这里主要压缩权重。小行数 kernel 按块读取编码、恢复数值并计算；激活和本轮 KV 使用 BF16，循环矩阵与一些累加使用 FP32。因此要区分权重存储精度与计算中各对象的精度。

**Q10：GPTQ 和本项目加载时的量化分别负责什么？**

主模型使用发布好的 GPTQ INT4 权重，本次没有重新做它的校准。MTP 部分的某些 BF16 权重则在加载时做按组的舍入量化，叫 RTN。二者的生成过程不同，不能只因为最后都是四位存储就混为一谈。

**Q11：PyTorch 和 Triton 各做了什么？**

PyTorch 负责张量、设备内存以及调用和图管理等工作。Triton 用来描述专门的 GPU kernel，例如压缩权重的读取与计算、多个操作的融合；两者在同一个引擎里配合使用。

**Q12：算子融合与 CUDA Graph 分别减少什么开销？**

融合把若干操作合进一个 kernel，减少中间张量的读写和部分启动。CUDA Graph 保存一段 GPU 执行安排，重放时减少 CPU 逐项提交工作；一个 graph 里仍然可以有许多 kernel。

**Q13：输入 token 每步都变，CUDA Graph 为什么还能重放？**

把 token 和位置放在地址固定的设备缓冲区里，每次更新其中的值。图重放时从这些缓冲区读取新的内容，因此地址和安排可以保持稳定，数据仍然可以变化。

**Q14：这里的 eager 是什么基线？**

它是同一推理引擎不重放 CUDA Graph 的执行方式，已经使用该引擎的量化和融合实现。它不是另外加载的 Hugging Face BF16 模型。三者的比较用于研究这个引擎内部的执行变化。

**Q15：为什么测量前要预热？**

第一次使用可能触发编译、自动调优及其他准备工作。先完成准备并预热，再测量重复执行，有助于回答“模型准备好之后有多快”；冷启动则需要单独设计测量。

**Q16：验证四行是不是 batch size 4？**

这里的四行属于同一个请求的四个连续位置，仍然是单请求。多个输入行可以在同次矩阵运算中复用权重，但 attention 仍要遵守前后顺序，循环层也必须正确传递状态。

### 练习三：投机解码（对应第 6～7 课）

**Q17：MTP 的全称是什么，它与 Speculative Decoding 是什么关系？**

MTP 是 Multi-Token Prediction，多 token 预测；Speculative Decoding 是投机解码。在本项目中，MTP head 提供候选 token，投机解码流程负责让主模型验证候选并提交结果。每步猜三个 token，是同一个草稿 head 连续运行三次。

**Q18：主模型还要检查所有草稿，为什么可能更快？**

草稿已经给出了候选输入，因此主模型可以在一次调用里处理多个位置，让权重读取和执行开销服务多个 token。接受的草稿足够多、额外成本足够小时，总时间就可能少于多次单 token 调用。

**Q19：草稿是 B、C、D，主模型在 C 后预测 X，返回什么？**

假设前两项验证分别是 B、C，那么接受 B、C，在第三项拒绝 D，返回 B、C、X。原来已经输出的 A 只作为本轮输入，不再返回一次。

**Q20：为什么不能跳过错误草稿，继续接受后面碰巧对的词？**

后面的预测已经把错误草稿当成了前文。前文一变，预测条件就变了，因此只能接受从第一项开始连续正确的部分。匹配标记为 `[对、错、对]` 时只接受一个。

**Q21：三个草稿全部被接受，为什么还能多输出一个？**

验证最后一个草稿作为输入时，主模型也算出了它的后继分数。因此三个候选都正确时，还能返回主模型选出的下一项，共四个新 token；实际交付数量还受剩余输出长度限制。

**Q22：接受两个草稿后，为什么位置加三，而状态槽是二？**

本轮已经处理了原输入 A 和两个接受的草稿 B、C，所以有效位置前进三格。槽从零编号：slot 0 是处理完 A，slot 1 是处理完 B，slot 2 是处理完 C；新输出 X 留给下一步处理。

**Q23：被拒绝部分的 KV 和循环矩阵分别怎样处理？**

KV 的错误尾部可以留在物理内存中，只要有效位置和读取范围排除它，并在后续写入时覆盖。循环矩阵已经把输入混入记忆，需要选择保存的正确快照；仅改长度不能恢复矩阵内容。

**Q24：草稿词表为什么可以小于主模型词表？**

草稿只是提出候选，最终仍由完整主模型决定接受与后继。限制草稿词表可以减少草稿输出层的工作，但当正确 token 不在草稿词表里时，候选就无法命中，会影响接受率。

### 练习四：性能与排障（对应第 6、8 课）

**Q25：接受率 60%，每步猜三个，为什么不一定加速 2.8 倍？**

`1 + 3 × 60% = 2.8` 是末步截断前的平均可用输出数。一次投机步骤还包括三次草稿生成、多行验证和状态处理；只有把这些实际耗时计入，才能得到加速比。

**Q26：投机解码在什么情况下可能更慢？**

草稿经常猜错时，一步可能仍然只交付一个 token，却多付出了草稿和验证成本。输出很短时，准备成本也可能占得更多。选择深度和策略需要结合真实工作负载测量。

**Q27：三种方式各自重复稳定，是否说明它们相互一致？**

不说明。最初的三种方式各跑三轮都稳定，但投机方式在英文、代码、中文上分别从索引 20、61、69 开始与普通图路径分叉。重复稳定与跨方式一致是两件需要分别检查的事。

**Q28：输出收集和位置计数都正确，还可能哪里不对？**

历史状态的数值内容，或者产生 logits 的计算路径，都还可能不同。计数说明“用了哪个位置、返回了多少个”，没有证明“这些位置存的数是否一致”。所以后续要固定状态、比较内部数值。

**Q29：为什么固定 hidden 检查 lm_head？**

最终分数不同，可能是输出层之前已经不同，也可能是输出层自身的执行差异。固定同一份 hidden 后测试几种输出层路径，就能隔离这个环节。本次这些投影逐值相同，而实际传入的 hidden 早已不同，于是继续向前查。

**Q30：很小的浮点差异为什么能改变生成结果？**

选词取决于候选之间的相对分数，而不是只看差值绝对大小。真实分叉里，executed 从 21.75 变为 21.625，与 granted 打平，最终选中另一个 token；第一处变化又会改变后续前文。

**Q31：什么证据支持统一 Gated DeltaNet 分块？**

从相同状态计算相同输入，原设置有 1246 处观测不同；只统一该分块后，1365 处观测全部相同；单独统一量化投影配置仍有差异。这个控制实验给出了局部修正依据，随后再通过完整生成验证。

**Q32：修正具体改了什么？**

一致性模式中，把 Gated DeltaNet 的 `BV` 固定为完整 value head 的维度，使单行和四行都走对应的完整 head 路径。本次 head 宽度是 128。没有修改最高分选词规则，也没有放宽逐 token 的判定条件。

### 练习五：实验结论与个人工作（对应第 9～10 课）

**Q33：Gate 已经通过，benchmark 为什么还比较输出？**

要确认计时实际使用的设置和行为仍然符合预期。项目曾出现一致性 gate 通过、正常性能路径仍分叉，因此后来对齐执行设置，并把 benchmark 输出同时与本轮参考和保存的 gate 参考比较。

**Q34：2.00～2.26 倍加速说的是哪段时间？**

首 token 之后的解码。在本次固定输出 128 个 token 的情况下，用后续 127 个实际输出除以后续生成时间；不能把这个比值直接套到首 token 延迟或包含首 token 的整个请求上。

**Q35：GPU 是异步的，怎样避免只测到提交时间？**

在计时边界等待 GPU 完成，并把每步取回 token 和同步的开销计入 CPU 侧时间。这样测的是这条生成流程真正完成所用的时间。若想单独研究某个 GPU kernel，则要另做对应的计时实验。

**Q36：最后一步多算出的 token 怎么计数？**

只把目标长度以内、实际留下的 token 算进速度分子，整步耗时仍然保留。例如还差一个输出而这步算出四个，就只计一个输出，另三个记作丢弃尾部。

**Q37：为什么用三轮中位数，是否足以说明普遍性能？**

中位数可以减少单次极端值对这组汇总的影响，但三轮仍然是很少的重复。本次结论适用于记录的三条输入和配置；要研究长期稳定性、尾延迟或更多类型任务，还需要增加对应样本。

**Q38：投机多占约 0.564 GiB，能说都是 KV cache 吗？**

不能。这个数来自两种方式的 PyTorch 峰值 allocated 对比，包含草稿模块、额外缓冲区和图相关分配等变化。归因到某一部分需要拆开统计，并且当前数值只对应这套配置。

**Q39：如果继续做，你先设计什么实验？**

可以先固定模型与输入，改变草稿深度，比较接受率、每步耗时、实际输出速度和显存，寻找成本与接受收益的平衡。每个新配置都要配套检查输出；之后再扩展输入长度与任务类型，让每轮实验回答一个具体问题。

**Q40：项目中哪些是已有实现，哪些是你完成的工作？**

推理引擎、量化内核、CUDA Graph 和 MTP 的基础实现沿用 Token Rush。我在此基础上完成单卡复现、统一实验入口与记录、分叉诊断工具、一致性模式的局部修正，以及匹配配置的输出核验和性能对照。介绍系统时可以解释整条技术链，说明个人工作时则落到这些具体改动和证据。
